## Next falsifiable mechanism, pending first-batch data

**VERIFIED (source observation):** the pinned public encoder `validator/measure/src/deflate.rs` uses `BLOCK_TOKENS = 16384`, builds dynamic length/distance alphabets from token frequencies, and includes the full encoder execution in the measured time. `run1` currently takes every valid length >= 3 reported by `probe_m`, irrespective of the existing `gain` estimate.

**INFERRED:** prose length-4 matches with distance > 2048 are negative in the parser's existing cost proxy: four literals are valued at 20 bits, while its match base is 10.5 bits and the distance has at least 10 extra bits. Refusing that narrow class needs no additional probe or table traffic and may save both distance-symbol cost and a bad greedy choice. It may also increase literal tokens and slow the encoder or miss useful backward folding. This is therefore a candidate for a later small batch, not a demonstrated optimization. Actual dynamic Huffman costs depend on each token block, so the proxy alone cannot establish an output-size gain.

**VERIFIED (source checks only):** the new generator's SHA locks and exact `--check` pass. Each source differs from fast3 on exactly one main-loop acceptance line. Prose has `P_SKIP=5`; all other live `run1` classes pass skip 3 or 4. This frozen-base distinction gates the new condition without adding a function argument or loop state. The generator asserts these constants. Class-5 tiny text still routes through `run1t`, which is untouched; the affected path is the larger prose `run1` path.

Rejection takes the existing miss branch after `head_set` and the p+1 prefetch have already occurred. That branch advances p, increments miss, and either retains the correct p+1 prefetch or refreshes it after a skip. `ins` exists only inside the accepted branch; rejection does not use it. The fuel decrease and all loop state shapes remain unchanged. The backward-rescue predicate guards both byte loads with `f.1 < p`; it preserves only a possible fold, not a proven profitable fold.

**INFERRED:** cost2048 isolates removal of matches with negative existing proxy gain; cost8192 tests a less aggressive cutoff. The backward-rescue variant tests the concrete confound that a currently short match can become valuable after backward merging. Since rejection grows miss and can increase skip acceleration, any timing gain cannot be attributed solely to avoiding one match token. Performance can improve or regress on either axis.

Two new hypotheses, frozen before measurements:

1. `r4-parse-lazy4far`: `P_LAZY=5`, and prose lazy body requires `d > 2048`. Only length-4 far matches (negative current gain proxy) get an extra next-position lookup. This duplicates a necessary test from `probe_lazy` before those side effects; whether the compiler shares the input load is **UNKNOWN**. A skipped failed lazy step changes which interior match positions are recorded, so no token-equivalence claim is made.

Both use general match properties and keep all non-prose lazy thresholds unchanged. They add no loop state or larger table. Fresh official extraction and gate remain necessary, especially for the prefilter's new `be8` call in the loop guard.
