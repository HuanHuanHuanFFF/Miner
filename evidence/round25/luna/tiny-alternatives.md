# Tiny-config alternatives and timing evidence

**Byte evidence is verified; tiny-tail total-time cost remains unknown.** The archived public-28 comparison records `tiny-config.json.txt` (12,000 raw bytes) as 2,155 bytes with public #584, 2,487 bytes with public #595 and `combo`, and 2,077 bytes with public #609. #595 and `combo` have identical token and output hashes on this file. Public #609 is the 2,077-byte row; that result does not belong to #595.

The R25 native original-encoder receipt for `r25-astra-tiny-tail` records 2,479 output bytes and 3,072 tokens, versus `combo` at 2,487 bytes and 3,094 tokens. This saves 8 bytes and 22 tokens on `tiny-config.json.txt`; the other 27 public files are unchanged. The equal-file aggregate change is only 0.00238095 percentage points. The receipt establishes bytes, not performance.

| Source | 12 KB dispatch | Engine and match path |
|---|---|---|
| Public #584 | `bulk_parse`: length 12,000 calls `p135_row3`; that row calls `pc_run1::<32769>(…, 6, 16, 1_000_000, 0xffffffff)`. | A PC run-one parser with 32,769 last-position hash slots, a 4-byte key, per-position probes, lazy lookahead and skip-on-miss behavior. It folds prior tokens and emits through the PC match path without ETINY’s restricted length-piece mask. |
| Public #595 and `combo` | `route`: length 12,000 returns class 23; `bulk_parse` class 23 calls `p125_row12`, which calls `et_tiny(input, out, 302256384)`. | ETINY uses a 4,096-slot one-way table keyed from four bytes, queries roughly every eight bytes, extends and folds matches, then emits allowed-length pieces from the mask. A short remainder that fits no allowed piece stays pending/literal. |
| R25 `tiny-tail` | Same route and `et_tiny` entry as `combo`. | Adds `et_piece_tail` to the coverage and emission selectors. When the greedy allowed piece would leave a remainder shorter than the minimum allowed length, it tries two allowed pieces and accepts them if they cover more bytes and their estimated match gain is higher. The search, route, and table stay the same. |

So the 8-byte repair is a match-segmentation component inside ETINY, not a route-constant change. Public #584 is a separate parser-engine option: its 332-byte advantage over `combo` comes with a different table, lookup cadence, lazy-match behavior and emission policy. Reusing that engine would be a separate port and proof task; its runtime on this input is unknown. The archived source receipts retain #584 and #595 authorship and file hashes in `references/round18-public-584/` and `references/round21-public-595/`.

The R24 “tiny” negative concerns another mechanism. `r24-609-tiny-converge` tried to stop the `SFtinytokens` reassignment loop after a rejected trial while keeping improving trials. Its dispatch calls that path at 28,000 bytes; `tiny-config.json.txt` is 12,000 bytes. The R24 instrumented count receipt shows the target file made 0 rounds, while `tiny-app.log` made 2 rounds with 1 improvement and 0 rejected trials followed by a remaining round. R24 therefore found no early-stop work to remove on the public corpus. This does not test ETINY’s restricted-length tail splitting. The older R18 exact-price DP repeat check is another separate path.

There is no standard total-compression time receipt for the R25 tiny-tail source. `feedback-b-native.json` states `timing: NOT_MEASURED` and `full_gate: NOT_RUN`; its referenced encoder receipt contains byte/token outputs only. None of the 56 Round 25 JSONL files contains either the tiny-tail candidate name or its Rust hash. Standard control measurements for `combo` and #595 exist, but without the tiny-tail source measured in the same runner and batch they cannot identify its added time. Keep that cost **UNKNOWN**.

**Decision:** the actual 8-byte change justifies at most one isolated `combo` versus `tiny-tail` original-standard paired timing screen, if the round has room for it. That screen should use the same runner and batch, retain the per-file total-time rows, and judge the 28-file score. The byte gain alone does not support a full gate or a stable ranking claim. Public #584’s larger byte result should remain a separate engine-port question.

Evidence and hashes are collated in [tiny-alternatives.json](tiny-alternatives.json). The R25 selector model is finite-model evidence only; the candidate’s saved Lean hash matches `combo`, but this exact Rust/Lean pair has no new full-gate result.
