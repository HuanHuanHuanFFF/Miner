### Ring-minimum update chain

`r6-h16-cpu-rm-inline` adds `inline(always)` only to `h_rm_update`, `h_rm_update3`, and their dispatcher `h_rm_upd`. It does not annotate the larger DP functions or all H helpers.

The frozen source shows `h_rm_upd` called once in each iteration of the backwards byte loops in `h_dp_prune` and `h_dp_items`. It branches on `l4` to perform the original ring-minimum update with four/five levels. `h_rm_update` also initializes the ring once in each block-pass wrapper. Making just this bounded chain available to its callers may remove per-byte calls/argument passing or expose a stable `l4` branch. The release compiler may already do that; the hypothesis has no established machine-code benefit yet.

### Cached-query replay kernel

`r6-h16-cpu-replay-inline` adds `inline(always)` only to `h_relax_items` (parent line 3873, 667-byte declaration, SHA256 `5baea55017fefeec4fbba13e3813ceb0b6eccc6b772e88ac281a795d3f5b04e4`). Its only syntactic caller is `h_dp_items` at line 3959. That caller traverses backward bytes and invokes the cached-query scan for each byte; `h_dp_pass` selects this replay path when `pr != 0`.

The single annotation tests removing that per-byte boundary and exposing the replay loop to the surrounding byte loop. It preserves every recorded query, query order, match cost, best-choice update and ring update. No iteration or cache budget changes. Actual replay counts and how often the compiler already inlines the function are UNKNOWN. Unlike a broad outline/inlining bundle, this variant isolates one kernel and is independent of the ring-update variant.

**Falsifiable diagnostic:** Check baseline/shadow/candidate `h_dp_items` and `h_relax_items` symbols/calls and resulting body size. Attribute-induced duplication, register pressure, or no change at all are possible. Do not combine this with ring inlining before the individual measured effects are known.

## Previous experiments constrain interpretation

`ROUND4.md` and `evidence/round4/cpu-notes.md` record CPU experiments on the fast3/#432 family, not these H functions:

- Disabling fast3 read-ahead regressed total time by about 1.78%; outlining its main `run1` regressed about 4.32% and lost constant specialization. Neither mechanism is repeated here.
- `run1t` inlining and zero-flush had small initial improvements that did not independently reproduce. `classoutline`, delayed second loads, slot-only and related source rewrites did not establish a stable CPU gain.
- Same-process order reversal changed the sign of several small effects. A source-level reduction, single runner, or favorable block is insufficient for adopting these variants.
- H8 core trimming reduced proof cost, but it was not an algorithm speedup. Later H16/depth/mode experiments change search/refit policy and are not CPU evidence for these attribute-only variants.

The fixed candidate release profile is already `opt-level=3`, fat LTO, one codegen unit and overflow checks enabled (`sources/conjectures-optimisation-deflate/validator/measure/candidate/Cargo.toml`). There is therefore no assumption that the compiler currently lacks inlining. The [Rust Reference](https://doc.rust-lang.org/reference/attributes/codegen.html#the-inline-attribute) describes inline modes as code-generation hints; the compiler may ignore them, and poor inlining choices can hurt performance. This is why the planned same-binary assembly diagnostic is part of interpreting a result, not an optional proof of benefit added afterward.

Assess candidate-versus-H16 movement alongside the same-source shadow and order blocks; do not discard unfavorable blocks.

- Any observed token/output difference is a failure of the intended CPU-only identity experiment and must be localized to its first differing input before adoption.

- Stop an individual variant if paired total compression fails to improve consistently, if replay-heavy files regress enough to outweigh a gain, or if code growth causes a stable slowdown. Parser-only improvement is not the competition objective.
- Preserve positive screening as measured evidence, then run the complete fresh gate at unchanged limits. A public CPU/gate improvement remains separate from private transfer, live frontier placement and payment.
