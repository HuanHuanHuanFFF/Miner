# A20 后续建议：将逐调用 CPU 与同源码阶段波动关联

状态：仅建议，未实现、未编译、未派发，不占用本轮已冻结的研究窗口。

缺口：A20已经证明本次原engine的CPU0请求没有形成单核限制，并观测同一PID在CPU0与CPU2执行；然而4Hz的最后执行CPU采样无法对齐具体文件、rep、parser/encoder阶段。A19分段时长移动的原因仍UNKNOWN。R24的显式绑核效果不一致，直接再扫绑核/ASLR/重复次数难以区分原因。

最小动作：一台临时runner，两份依次运行、同路径同哈希public658 DSO与incumbent的独立原配对进程。仍28文件、1预热、11次、原顺序和sandbox请求。复制原测量引擎到scratch，仅在已有parser及encoder计时区外记录单调时钟、file/rep/method/stage以及getcpu前后值；开始前CPU查询必须先于原start计时，结束后查询必须晚于原elapsed读取，记录写入预分配数组并在末尾输出。绑定scratch diff、原/新engine哈希及原token/output/输入身份，不改官方树。实际affinity和PID/cgroup继续按A20方法保存。

只比较两个问题：同一文件、同一阶段、同一CPU前后值的多次调用是否仍分成明显时长带；时长带切换是否与CPU值改变同步。相同CPU前后不能保证中间未迁移，所以保留这一可见性局限，不当作CPU周期测量。

判别与停止：

- 如果同CPU前后值仍有相同程度的带状波动，迁移不能单独解释该诊断中的所有波动；后续再调查频率／主机状态／布局，当前不选一个根因。
- 如果变化与CPU值高度同步，只建立关联；下一次才考虑一个明确固定CPU干预，而不是本批同时加多种条件。
- 若未出现波动或CPU变化，报告未复现，不自动补跑或宣称修复。

计时区外遥测仍可能扰动缓存与调度，所以全部时长都是diagnostic，不复算候选份额、不替代原协议结果、不据此确认稳定收益。建议25分钟cap、只这两个进程；原build/measure限时维持。是否投入应由下一轮的具体候选和晋升分歧决定。
