# Public log2: compiler source reopens the cheap-normalization premise

Scope: source-only follow-up to STERBENZ-PREMISE, first new source query23:32 UTC. No local compiler, candidate/public operation, CI dispatch, or performance sample. Broad-word runtime5655 and complete diagnostic0274 remain frozen. Source inputs and their Git blobs are in log2-source-index.json; verification is separate.

The fixed Lean293d5d0c public UInt32.log2 and UInt64.log2 use existing runtime bindings. In the pinned header, UInt32's implementation is an inline shift/divide-by2 loop with an unsigned counter, while(a>=2). Reading that loop alone did not establish its optimized cost.

New primary chain: fixed Lean's [.github/workflows/ci.yml](https://github.com/leanprover/lean4/blob/293d5d0c0c3f3dded4688b3ccd6a33939ac5102b/.github/workflows/ci.yml#L302) selects lean-llvm22.1.4 for the Linux release. That release's [build workflow](https://github.com/leanprover/lean-llvm/blob/22.1.4/.github/workflows/build.yml#L92) builds the llvmorg-22.1.4 tag. The captured cost3 compile argv uses the bundled Lean4.34.0/bin/clang with O3, but contains no actual clang --version result; binding the installed binary to that declared release remains INFERRED.

LLVM22.1.4 has a specific [floor-log2 loop recognizer](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.4/llvm/lib/Transforms/Scalar/LoopIdiomRecognize.cpp#L2487). It requires a single-block/single-backedge unsigned right shift by1, counter +/-1 recurrence, and a threshold comparison. For floorlog2, the rotated backedge threshold is4, the preheader threshold is2, and only the incremented counter may escape. It requests ctlz, subject to its instruction-cost check, then makes the loop countable. Subsequent removal of the now dead loop is separate compiler work.

The same tag's [official test](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.4/llvm/test/Transforms/LoopIdiom/AArch64/ctlz.ll#L457) has `floor_log2_use_inc`: initial n<2, logical right shift, increment, old n<4 backedge. Expected output contains llvm.ctlz and a computed count. This is an AArch64 IR pass test, not an x86 machine-code test or one executed here. A companion test `floor_log2_use_phi` intentionally retains the loop, illustrating that the escaping value matters.

**Inference:** the pinned lean_uint32_log2 loop plausibly reaches the recognized form after unsigned divide lowering, rotation, and comparison canonicalization. This materially weakens the prior assumption that it costs up to23 iterations. It does not establish actual generated code, a single bsr/lzcnt instruction, latency, or package gain. Prior source-only 12.9–15.7 iteration averages must not be treated as machine timing.

Smallest next discriminator is Probe-log2-public-api.lean.inc: two noinline ordinary public wrappers plus rfl equations, no new extern/unsafe/intrinsic/implementation override and no operation selector. If D chooses to include it in already authorized codegen work, inspect the exact generated word32/word64 bodies with actual compiler version/flags: backward branches versus ctlz lowering/bsr/lzcnt and zero handling. It is not a performance entry and must not be timed as a replacement operation. Actualcaller cost remains necessary before a Sterbenz/full-add extension; original narrow-domain exposure screens remain binding and unchanged. No proof expansion until that prerequisite and a sufficiently broad integration justify it.

Existing B2 `FastMul.fastLog2_eq` already proves its binary-search UInt64 helper equals public UInt64.log2, but this does not authorize replacing B2 or imply a benefit: most retained scalar branches bypass that helper. A possible all-sign direct word ADD would need separate exact cancellation, normalization, sign/zero, subnormal and rounding proofs. None is supplied here.
