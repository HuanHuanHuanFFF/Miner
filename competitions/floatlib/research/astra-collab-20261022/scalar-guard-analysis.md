# Scalar follow-up after current timing feedback

No new scalar candidate is queued yet. Current R2-04/R2-05 layout/fold set needs compiler evidence first, and D's no-raw-guard full timing may change the decision below.

Pinned lean.h declares native Float32 isFinite/isNaN/isInf as external functions, just like raw bit conversion. The scalar add/mul wrappers still call isFinite twice. The existing integer exponent check can prove the same finite-input condition without invoking those native classifiers at runtime. `word-finite-bridge-draft.lean` separates the raw Model proof from ExecFloat specialization to avoid the instance-rewriting failure seen in R2-01. It is NOT_RUN. Its public decoder lemmas were verified in pinned Narrow/Agreement.lean; no new arithmetic semantics are asserted.

Expected next experiment, if warranted: use raw exponent !=255 on both inputs, then the same proven native finite add/mul and original fallback. This retains native finite overflow results (unlike checking only the output for finiteness). It is a cheap source-level predicate change, but actual C and full-call timings must confirm any gain. Do not conflate it with already removed raw roundtrip equality checks.

Old per-class receipts expose a potential secondary multiplication issue. Exact native-both707d in full runs39590684208/39593447390 had mul:tiny ratios1.050375/1.192249 versus shipped, while near-one/spread were faster. On the latter runner tiny was16.358322ns vs13.720556ns shipped, compared with11.080426ns for native near-one. This supports checking hardware subnormal-result cost as an explanation, not asserting it. CPUs differ and these runs predate current guard removal. Fresh no-raw/word-guard timing could erase the regression; wait for that evidence before a hybrid.

If a subnormal cost remains, a proved software/native hybrid needs no new correctness assumption: both branch implementations already have exact specs. For normal inputs E1,E2>=1, E1+E2>=128 guarantees the exact product is at least the minimum normal magnitude. Using this merely as a performance routing threshold can avoid many subnormal hardware products while retaining exact fallback. The timed tiny domain has E1 in55..65 and E2 in50..60; every sum is below128. Spread covers1..254 and includes both underflow and overflow. Do not claim the threshold is optimal, do not exclude overflow from the existing finite-input native proof, and do not infer a timing gain from the class generator alone.

Historical rebuilt-mul proof1 is a distinct software implementation and a possible fallback starting point, but any adoption requires exact integration and a new combined full gate. Separate old class ratios cannot be composed into a new package result.

Fresh feedback from full run39655361399 changes the hybrid priority: same-run native-both control still has mul:tiny1.057790 versus shipped, but removing raw guards gives0.946486, so the old tiny regression is no longer present against that reference. Final-finite parent39656662501 gives0.925778 on its separate runner. Do not automatically route tiny products back to old software from the historical regression. Prioritize the raw-word finite proof and new exact timing; a hybrid now needs an additional controlled comparison against the actual current wrapper/fallback.
