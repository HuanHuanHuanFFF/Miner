# TinyPC public quality arithmetic audit

The `quality-i-native` receipt verifies a finite 28-file byte comparison: `combo` and `r25-root-tiny-pc8` use the same 28 input hashes, and only `tiny-config.json.txt` changes output. It goes from 2,487 to 2,155 bytes on the same 12,000-byte input, a 332-byte / 818-token reduction. The other 27 outputs and tokens match.

The official scoring document says the compression coordinate is the arithmetic mean of each nonempty file's compressed/raw ratio within a corpus; required corpora are then averaged equally. Thus the one file's ratio changes from 20.725% to 17.958333%, a **−2.766667 percentage-point** change. Since the file is one of 28 equally weighted rows, the 28-file corpus mean changes by **−0.098809524 pp**. This is why a 332-byte saving produces a comparatively large movement in the public per-file mean: file weight is not proportional to raw size. For contrast only, 332 bytes out of the set's 15.93 MB total would be −0.00208412 pp under byte weighting, which is not the official compression formula.

The −0.0988095 pp result is a `mean_file_compression_pct` calculation, **not** a `balanced_time_ratio` result. The official time coordinate uses paired per-file total-time ratios; this quality receipt contains no timing. Snapshot 29678 and the prior 29677 have the same 626 Pareto IDs, the same 585 leaderboard identities/ranks, and unchanged row-level gate, admission, frontier, and weight fields. The official scoring document also equally weights the required `corpus-stage1` and `corpus-stage2` means. If these 28 rows were exactly one official corpus and stage2 stayed unchanged, the cross-corpus mean effect would be half, −0.049404762 pp; that is a conditional illustration, not a measured official result. This quality-only run does not establish the full official stage mapping or stage2 effect.
