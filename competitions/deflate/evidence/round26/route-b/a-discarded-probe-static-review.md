# A tree probes discarded by the increasing-length frontier

This is read-only investigation while B13's one permitted ordinary-overlap candidate waits for its native checkpoint. No additional candidate, observer or CI has been prepared for this route.

VERIFIED source facts: original #552 `a_tree_insert` already computes the LCP of its recent-root hint and each visited tree node, but appends a record only when `length > best`. Every appended record is a longer extent than the previous one. A shorter visited candidate with another distance-symbol price can therefore be absent from the DP cache, unlike B12's already-existing inherited continuation. This is a missing candidate-source question, not another choice among unchanged records, increased tree depth, or a new tree matcher.

Historical exclusions inspected: R8D reselected distances among existing increasing-length records and gained no bytes. R9 transplanted a different tree into D, gained longer matches but had enormous finder cost. R24 L/V retained more already-found SF distance-code choices in four/eight-slot collectors, recovering only 11/22 bytes; those collectors and their existing retention/filter policy are distinct from A's increasing-length frontier. R24 X searched additional weak-match positions and gained 69 bytes at ~4.2% total cost. R24 AN coalesced adjacent same-distance A records, preserving offers; it did not retain shorter visited matches. None of these inspected experiments directly establishes a native outcome for the current #552 discarded-probe source. They are negative context, not evidence this source will succeed.

A possible minimum check would preserve all original tree/cache/XL/XD/DP state and tokens, observing the already computed discarded LCPs. It must count how many length≥3 byte-valid candidates survive per-distance-code maximum-length dominance, and compare actual original-pass prices and original final packed best on their covered lengths. Raw discarded-node count, novel code count or low fixed extra-bit price alone would not justify implementation. Actual full/sampled prices matter, and a discarded same-code shorter candidate need not be useful.

First effective checkpoint dependencies and costs: an observer would need to carry per-position retained discarded candidates from original matching into the unchanged DP trajectory, so producer-only counting is insufficient. A bounded logical representation could retain one longest valid discarded prefix per 30 legal distance symbols; within a code all offered lengths have the same dc price, although tie/choice provenance still needs a fixed rule. Worst-case logical storage is 30 records×4 bytes per raw position plus an offset table, up to 124*n bytes (about 124 MB for a 1 MB input); this is an upper storage accounting bound, not measured memory or free cost. Reset/slot maintenance per searched position, byte validity checks, append/traversal, every-price-pass queries and actual range reductions must be counted. A 15–20 minute native cap would have to be accepted by root before writing this observer, and would not include any production performance or proof acceptance.

Selection boundary: if actual useful packed-best changes are sparse, stop without building a 30-slot production cache. If concentrated useful additions remain after same-code dominance, then one complete variant would still need a cost-conscious consumer, actual original encoder quality, original-protocol paired timing, exact extraction/proof/gate and frozen independent confirmation. A small quality improvement can be worth preserving, but cannot be called a stable 5/10% candidate without those steps and same-snapshot joint scoring.
